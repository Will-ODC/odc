## Verdict

# APPROVE WITH NITS

This audit found **no blocking finding and no charter violation**. Each of the
six blocking findings from the 2026-08-14 audit (F1 to F6) is resolved in the
current spec text, and each has fixtures. I rebuilt the F1 and F3 attacks
against the current rules. Both verifiers now reject them when given the
anchor. Both verifiers agree with `index.json` on all 145 vectors. They also
agree with each other on 8,000 random batching chains, 1,898 of which reach a
`PARTIAL` verdict.

Seven `[SHOULD]` findings remain, and none of them gates RC. RC keeps the specs
fixable, and every SHOULD below can be fixed in one of three ways: a
producer-side rule that changes no verdict, a new fixture, or a fix to a
document outside `contracts/`. None needs a change that would make an
existing conforming chain retroactively invalid. That kind of change is the
test the previous audit used to decide what had to land before freeze. Three
of the SHOULDs (S-A, S-B, S-C) constrain the **ledger write path** and the
**identity signing flow**. Those are the first things Phase 1 builds, so fix
or decide them before that code is written, not after.

## New findings

None is `[BLOCKING]`.

### [SHOULD] S-A: No contract rule requires the ledger to verify an event before appending it, and one unverified append poisons the chain permanently

`read-api.md:87–90` (RA-13) places the write path "outside `contracts/`".
`evolution.md:457` (EV-25) is the only general producer MUST, and it limits line
size. Nothing in `contracts/` says a ledger MUST NOT append an event that would
make its own export `INVALID`. That gap matters because `evolution.md:77–78`
(EV-7) says verification stops at the first fatal line: "the chain is tainted
from there". The log is append-only, so that taint cannot be repaired.

`participant_registered` is self-signed by a member of the public (ET-10). So a
ledger that hashes and appends whatever it is sent lets **any registrant**
break the governance record forever, with one bad signature or one
non-canonical key. **Demonstrated** (`poison-pill.ndjson`): a registration
with a corrupted `sig` is appended, with its hash recomputed so the chain still
links, and three valid ballots follow it. Both verifiers report `INVALID at
line 6`, and nothing appended later can fix that.

**Fix:** add one producer rule, for example in `evolution.md` next to EV-25:
"A ledger MUST NOT append an event unless the export with that event appended
verifies `VALID` (or `PARTIAL` only for events at versions newer than its own
registry) under a verifier registering the ledger's contracts version.
In particular, every Stage B signature check (ET-4a to ET-5) runs before the
append." This rule is producer-only and changes no verdict.
`services/ledger/CLAUDE.md:4` hints at this ("Validation is self-contained") but
does not say it.

### [SHOULD] S-B: ET-25 implies, but does not say, that a batch is released whole

`event-types.md:790–793` (ET-25) requires a batch's append order to be
"independent of the order in which they arrived". `event-types.md:622` (ET-24)
lets other events "fall between a batch's members". Read strictly, ET-25 does
the work. Any ledger that appends a ballot before the last ballot of its batch
has arrived produces an order that depends on arrival, so the only conforming
strategy is to hold the whole batch and release it at once.

A plainer reading leaves a loophole. The rule says "MUST NOT append a batch in
arrival order", and a ledger can satisfy those words by drip-feeding: shuffling
small groups, or appending each ballot as it arrives at the quantized `ts`.
Under drip-feed, an observer who tail-polls `GET /events` (RA-12) learns each
ballot's wall-clock arrival time, which is exactly the F2 attack. So does
anyone who later reads the millisecond `ts` of public-plane events interleaved
between batch members.

**Demonstrated** (`drip-feed.ndjson`): three ballots of one batch, each placed
straight after a `participant_registered` stamped 10:01:05.101, 10:01:21.456
and 10:01:40.002. Both verifiers report `VALID`, as they must, because ET-25
cannot be checked. Each ballot's arrival is pinned to within one registration.

`services/ledger/CLAUDE.md:5` already says "a batch withheld until it holds
`ballot_batch_min` ballots". So the obligation exists in a service's guide
file but not in the contract.

**Fix:** add one sentence to ET-25: "No ballot of a batch is appended until
the producer has closed that batch. A closed batch is appended in full, with
no further ballots of that issue at that instant." Also state in ET-21's
residuals that k-anonymity against a timing observer is
`ballot_batch_min`.

### [SHOULD] S-C: The registrar must sign each ballot's final position in the log, so the identity service sees where every ballot lands

`hashing.md:134–139` (HA-15) builds the signing preimage over `seq`, `ts` and
`prev_hash`. ET-17 (`event-types.md:484–486`) makes the registrar the signer of
`vote_cast`, and ET-9a puts that key only in the identity service. Together,
these mean the registrar can sign a ballot **only after the ledger has fixed
its final `seq` and predecessor**. It signs in the ledger's append path,
ballot by ballot, after the ET-25 shuffle.

Consequences the spec does not state:

1. `event-types.md:532–534` (ET-21) says the registrar sees
   `{voter, issue, choice}` "at admission time". In fact it also sees each
   ballot's exact line in the public log. Unless Phase 1 deliberately
   separates admission from signing, the identity service, which also holds
   the linkage map, becomes a voter-to-log-line join. This touches the first
   question on this audit's checklist ("Can any query path join ballot data
   and identity data?").
2. The ET-25 shuffle protects nothing against the registrar. It sees both the
   arrival order and the final positions.
3. It conflicts with `services/ledger/CLAUDE.md:4` ("no calls to other
   services"). Either the ledger calls identity at append time, or identity
   becomes the appender of every batch. Each signature also binds
   `prev_hash`, so any interleaved append makes a pre-signed batch worthless.

The spec leaves room for a clean design. For example, admission could record
only "voter V has voted on issue I" and keep an unattributed pool of
`(issue, choice)`, which the signer then consumes. But nothing requires such a
design. **This needs design work before the Phase 1 identity and ledger write
path is built.** The ET-21 wording fix (state the residual honestly) is
additive and can land any time. See "Design questions for filing" below.

### [SHOULD] S-D: The anchoring record is still specified nowhere (carried from S3)

`event-types.md:185` (ET-7a) refers to "an anchor or witness record
(charter §4)", and ET-7a now fixes **what** that record names: the
identity-and-head pair. No spec fixes its format, cadence or venue, or how a
reader detects a missing anchor. `export-format.md:108` (EX-15) keeps `--head`
optional.

With F1 fixed, a **common-prefix fork** is the operator's remaining
equivocation path. I demonstrated it with `fork-x.ndjson`, which shares chain
A's genesis hash: under `--chain <A>` it is `VALID` on both verifiers, and
only `--head <A's head>` rejects it (`INVALID at line 8`). So between anchors,
or wherever readers do not compare against a published anchor, two audiences
can be shown two suffixes. That is inherent to a transparency log without
gossip, and charter §4 accepts it. But third-party checkers cannot
interoperate on an anchor whose bytes nobody has specified.

**Fix:** a short additive spec, or an `export-format.md` section, for the
anchor record: genesis hash, head, `seq` of the head, and how a sequence of
anchors is shown to be consistent. Do this before the ledger publishes its
first anchor.

### [SHOULD] S-E: Still no fixture for ill-formed UTF-8 (carried from S4)

`hashing.md:44–45` (HA-2) closes with "MUST reject a string whose decoded value
is not well-formed UTF-8". No vector exercises it: I searched all 145 notes,
and the raw bytes, for surrogate and ill-formed cases. I constructed six cases:

- raw `ED A0 80`;
- an overlong `C0 80`;
- `F5 80 80 80`;
- a truncated `E2 82`;
- an escaped `\ud800`;
- raw octets hashed as their U+FFFD substitutions.

Both verifiers report **`INVALID at line 2` on all six**, so this is a gap in
coverage, not a divergence. Add at least the raw-surrogate and escaped-surrogate
vectors while `fixtures/` is still editable.

### [SHOULD] S-F: `services/ledger/CLAUDE.md:7` contradicts ET-10, which T9a must catch

`services/ledger/CLAUDE.md:7` says "participant_registered → identity service
key". But `event-types.md:393–395` (ET-10) makes `participant_registered`
self-signed under its own `pubkey`, as proof of possession, and fixtures
002/078 depend on that. A ledger built from the guide file would check the
wrong key. `services/*/CLAUDE.md` is on T9a's named reconciliation list. This
item belongs on that list, together with the "withheld" sentence from S-B and
the "no calls" sentence from S-C.

### [SHOULD] S-G: No key-compromise or rotation path, and nothing guards against reusing the test keys (carried from S5; gates the freeze, not RC)

The warning about the published test seeds lives only in
`fixtures/derivations.json:24`. Since then, `event-types.md:348–352` (ET-9e)
has closed the `genesis` payload for good. So any future key rotation must
arrive as **new versions of every signed type**, each signed under a key that
some new event declares. A `contracts-v1` verifier would then report `PARTIAL`
on that chain from the rotation onward. That is acceptable under EV-8, but it
is a design that does not exist yet, and leaking `registrar_pk` today lets an
attacker forge ballots that cannot be told apart from real ones, back to the
start of the chain. Decide this before the freeze. A deny-list of the
`0x01…01` and `0x02…02` keys at genesis would cost one comparison per key in
the ledger.

## The three Phase-0 gate questions

**1. Does any spec field leak identity into the public log?** No direct
leak. `vote_cast` is `{issue_id, choice, sig}`: it holds no voter key and no
participant id (ET-21). `participant_registered` holds only a pseudonymous
`pubkey`, which is public-plane by design (charter P2). The only free text is
`issue_created.title` (≤200 scalar values) and `genesis.contracts` (≤64
bytes), and the operator writes both. Read-API errors are the two fixed codes
of RA-11. Verifier output is a verdict plus stored hash claims (EX-24). The
linkage map appears nowhere in `contracts/`.

The remaining channels are outside the log's fields:

- the registrar signature channel (ET-21 residual, Q-F);
- the registrar seeing each ballot's position (S-C);
- registration-to-batch adjacency (ET-21 residual);
- turnout arithmetic (ET-14b note).

**2. Is receipt-freeness compromised by any spec artifact?** Not against a
voter acting alone: the voter holds no key and cannot predict `hash` or `sig`,
and ballots share no field. Against a coercer who watches the voter, the
millisecond `ts` channel is closed (ET-23), and a conforming ledger now
publishes in batches of at least `ballot_batch_min` (≥3) with no arrival order,
provided ET-25 is read strictly (S-B). Two bounded channels remain, both
documented. The first is a marker vote among up to 64 choices.
`marker-64.ndjson`, with one ballot at choice 41, is `VALID`. That ballot
proves only that _someone_ chose 41. The limit on choice count is an open
question that charter §5 itself names. The second is the registrar's
signature channel.

**3. Can the operator equivocate within the spec as written?** Two chains
under one key can no longer pass as one chain: they have different genesis
hashes, and `--chain` rejects the wrong one (re-demonstrated above). A
common-prefix fork is detectable only against an anchored head. The anchor
record is unspecified (S-D), and the operator can still sign any suffix,
because it holds both its own key and, by policy only, separation from the
registrar key (ET-9d is necessary, not sufficient).

**The agent checklist:**

- _Ballot and identity join:_ no query surface for it exists in `contracts/`.
  The identity service's signing role is S-C.
- _Linkage fields in errors, logs or metrics:_ none defined.
- _A voter-constructible proof:_ none (see question 2).
- _Mutating or deleting events:_ EV-1 forbids removing a type or changing a
  frozen schema, and RA-13 forbids writes on the read API. Ballots have no
  correction path (EV-13). End-truncation is caught only with `--head`
  (EX-16). No storage code exists to audit.
- _Ballot and sentiment sharing a store:_ barred permanently (EV-22).
- _Signatures verified before append:_ every verifier path checks them before
  a verdict, but no contract obligation exists on the producer (S-A).

**Do the verifiers' verdicts follow from `contracts/` alone?** On everything
I checked, yes:

- My own encoder, written from `hashing.md` and `export-format.md` alone in
  about 60 lines of Node, reproduces the §6 digest `78ed980b…` and the
  signature, and is byte-identical to vector 001 on its first run.
- Both verifiers agree with `index.json` on all 145 vectors.
- Neither verifier's non-test source reads `contracts/fixtures/`, embeds a
  fixture hash, or reads the environment or the network (grep).

I did not read either verifier's source line by line (see "Not covered").

## What is sound

- **F1 to F6 were fixed in the rulebook, not argued away.** Each fix has a
  numbered rule, a fixture, and a sentence explaining why it had to land
  before the freeze.
- **The batching design (ET-14b, ET-22a to ET-25) is right.** Its parameters
  are declared on the log, the floors are permanent, an instant is closed once
  left, and blame lands on the line that proves a batch was not the last. It
  states openly that ET-25 cannot be checked. ET-22a's "one event, one ballot,
  only `vote_cast` carries ballots" is what lets a frozen verifier reason
  about ballot versions it cannot read.
- **ET-24b is a careful piece of work.** It is conservative and never
  `INVALID` out of ignorance, and a vector may pin it only where the
  conservative and exact rules agree. On 8,000 random chains mixing
  registered and opaque ballots, unregistered issues, and two intervals and
  minimums, the two independent verifiers never disagreed.
- **Hashing is still reproducible from the prose alone.** The fixtures
  regenerate byte-identically from `tools/fixtures-gen` (145 vectors, 151
  files), and `MANIFEST.sha256` verifies.
- **The EV-23 to EV-25 limits close the "conforming verifier, any limit" gap**
  with a writer cap and a reader floor that are both permanent.
- **Dependency hygiene from the 2026-10-11 scan is done:** `edwards25519`
  v1.1.1 and `go 1.27.2`.

## Design questions for filing (not filed)

My agent definition asks me to file findings that need design work in
`memory/OPEN-QUESTIONS.md`. The brief barred me from reading `memory/`, so I
could not check for duplicates, and **I did not edit it**. Suggested entries,

   so the registrar signs inside the ledger's append path and sees each
   ballot's final log position. How does Phase 1 keep admission (which knows
