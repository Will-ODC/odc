# Dependency scans, and the 2026-10-09 audit's leftovers

**Date:** 2026-10-11. **Tree examined:** `origin/master` at `c26127d`.
**Issue:** part of #315. **Not a phase-gate audit.** It does not stand in for
the T9 re-audit, and it says nothing about the core's contracts.

This report re-checks the claims of Codex's whole-repo security and
personal-information audit of 2026-10-09 against today's tree, records the
dependency checks it left undone, and names what nobody has examined yet.

## What was checked, and how

### JavaScript dependencies: checked, no known advisories

From the repository root, on `c26127d`, with pnpm 9.0.0 against the npm
registry's advisory endpoint, on 2026-10-11:

```
pnpm install --frozen-lockfile
pnpm audit --prod
pnpm audit
```

Both commands printed `No known vulnerabilities found`. That is a statement
about the advisories the npm registry knew of on that date for the versions in
`pnpm-lock.yaml`, nothing more. It is not a claim that the code is free of
vulnerabilities. The 2026-10-09 audit found advisories here; #199 fixed them
by updating the lockfile, and on 2026-10-11 the registry knew of no advisory
against the current versions.

### Go dependencies: checked, nothing reachable, two things to update

`git ls-files '*go.mod'` finds one module, `services/verifier`. It requires one
module, `filippo.io/edwards25519` v1.1.0, plus the Go standard library.
On 2026-10-11, with govulncheck v1.1.4 (Go vulnerability database at
`https://vuln.go.dev`, updated 2026-10-08 22:31 UTC) and the local Go 1.26.5
toolchain:

```
go install golang.org/x/vuln/cmd/govulncheck@v1.1.4
cd services/verifier && govulncheck ./...
cd services/verifier && govulncheck -show verbose ./...
```

govulncheck checks at three depths. Results:

| Depth                                     | Result                                                                                                             |
| ----------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| A vulnerable function the verifier calls  | **None found**                                                                                                     |
| A vulnerable package the verifier imports | 2: `GO-2026-4503` in `filippo.io/edwards25519` (fixed in v1.1.1); `GO-2026-6604` in `os` (fixed in Go 1.26.9)      |
| A vulnerable module the verifier requires | 20, all standard-library advisories in Go 1.26.5, fixed in Go 1.26.6 or 1.26.9; full list from the verbose command |

**Severity: low, not reachable as built.** govulncheck's call analysis found no
path from the verifier's code to any of the vulnerable functions. That is a
claim about today's call graph; a later change to the verifier can make one
reachable without touching `go.mod`.

The standard-library results describe the toolchain that ran the scan, not a
property of the repository. CI builds with whatever `actions/setup-go` resolves
from `go 1.24` in `go.mod`, and anyone who builds the verifier uses their own
toolchain, so their results can differ. Go supports only its two newest major
releases; with 1.26 current, a 1.24 toolchain no longer receives security
fixes, so CI's toolchain is likely worse off than the 1.26.5 one scanned.

**Recommended fixes, owned by the verifier's own isolated context (ADR-0034's
session or its successor), not by this report:**

1. Bump `filippo.io/edwards25519` to v1.1.1 or later in `go.mod` and `go.sum`.
   This is the verifier's only signature-checking dependency, so take the bump
   even though the advisory is not reachable today.
2. Raise the `go` directive or add a `toolchain` line in `go.mod`, so CI and
   readers build with a supported, patched Go (1.26.9 or later today), and record in the verifier's README which Go version a reader should build
   with.

### Container images: deferred until a deploy (operator decision)

The two pulse images (`apps/pulse/Dockerfile`, built on `node:22.22-alpine`;
`apps/pulse-web/Dockerfile`, built on `nginx:1.29-alpine`) and the
`postgres:17` image in `apps/pulse/docker-compose.yml` have **not** been
scanned for known operating-system or bundled-package advisories. On
2026-10-11 the operator decided a one-off image scan is not proportionate while
nothing is deployed, and that the scan belongs in CI when a deploy is near:
a step in `.github/workflows/pulse-images.yml` that scans the images it already
builds (Trivy's official GitHub Action is the usual choice), so no tool is
installed on anyone's machine.

CI builds both images on every PR that touches them (#212), so they are known
to build. Whether they contain known-vulnerable packages is **unknown**.
Nothing is deployed, so the images reach no user today; this becomes a real
gap the day pulse is served.

### Ongoing checks: GitHub Dependabot alerts are off

`gh api repos/Will-ODC/odc/vulnerability-alerts` returned `404` on 2026-10-11,
which means Dependabot alerts are not enabled for the repository. With them on,
GitHub watches `pnpm-lock.yaml` and `services/verifier/go.mod` and raises an
alert when a new advisory is published, which a dated report like this one
cannot do. Turning them on is a repository setting for the operator.

### Still open

1. **Pulse offers no sign-out (severity: medium, reachable once deployed).**
   `apps/pulse-web/src/api/http.ts` has `signOut()` and the API serves
   `POST /api/sign-out`, but no screen calls it. Session cookies last 30 days.
   On a shared browser the next person stays signed in as the last. Tracked in
   #315. At `c26127d` it waited on #302; #302 landed in #322 on 2026-10-12, so
   it is now unblocked (`pulse/315-sign-out`). No screen calls `signOut` yet.
2. **Go: `filippo.io/edwards25519` v1.1.0 and a Go 1.26.5 toolchain carry
   advisories (severity: low, not reachable as built).** Bump to v1.1.1 and
   build with a patched Go; see above. Owned by the verifier's isolated context.
3. **Container advisories (severity: unknown).** Deferred until a deploy; see
   above.
4. **Dependabot alerts are off.** A repository setting for the operator.
5. **How long `pending_claim` rows are kept (policy, not a defect).** Each row
   holds a `subject` (today, an email address) and a token digest. Rows are deleted only when a link is discarded
   unused (`pg-store.ts`, `discard`); spent and expired rows stay forever.
   Filed in `memory/OPEN-QUESTIONS.md`.
6. **What an email-provider error may write to logs (policy, not a defect).**
   `apps/pulse/src/identity/resend-mailer.ts` puts up to 500 characters of the
   provider's error body into the error that reaches the operator log. If the
   provider echoes the recipient or the message, that lands in the log.
   Filed in `memory/OPEN-QUESTIONS.md`.

### Secrets

false positive (`generic-api-key`) at
`tools/fixtures-gen/test/canonical-ed25519.test.ts:276`, a published test value.
No confirmed secret was found. That is not proof that none exists; Gitleaks
finds only what its rules describe. It was not re-run for this report.
