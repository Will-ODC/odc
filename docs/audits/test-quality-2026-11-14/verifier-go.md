## Prioritized findings

### 1. SHOULD / P2 — ES-20 rejection tests can pass with calendar checks removed

Locations: `internal/verify/event.go:153` and `:194`; `internal/verify/verify_test.go:57`; `internal/verify/ballot_test.go:269`; fixtures `030`, `031`, `032`, line 2.

All three timestamp rejection fixtures retain the original timestamp's hash and signature after changing `ts`. A verifier that accepts the malformed timestamp still reports INVALID at the exact expected line through HA-14. The independent HA encoder confirmed these recomputed hashes:

| Vector          | Recomputed line-2 hash                                           |
| --------------- | ---------------------------------------------------------------- |
| 030 bad syntax  | bcba75e6efe6d94d404fbf858ea79d099947cff1ec0fe3841013c92cf61c6063 |
| 031 February 30 | f787dcf822ebc2c11de2972c5592b66663cadcb7df840b940d9d0746bc2c538d |
| 032 leap second | 74a57e21bb32840ad900063fa862eccd0ae2709329a5324a791652bdfee4412d |

Each stores `189441b60a6b1338b9fdfc30e8127f264d34773e617d21a434439ea8fa5c5821` instead. The time-package comparison checks only acceptance of valid timestamps; its last-day input additionally comes from production `daysInMonth`. No direct negative `validTS` tests exist. Removing just the month/day/hour/minute/second bounds after the syntax gate leaves every existing positive date unchanged and leaves these rejection fixtures INVALID through their bad hashes. This is a real missing discriminating case, not merely a missing citation. Executed evidence: replacing the entire `validTS` body with `return true` passed the full existing suite. An independently sealed opaque event dated February 30 then returned PARTIAL at 2 under the mutant, while original code correctly returned INVALID at 2.

Add direct positive/negative timestamp boundary tables (month/day zero and overflow, leap/non-leap February including century rules, hour 24, minute/second 60), or correctly sealed opaque-event chains whose only fault is the timestamp. A malformed unknown event with independently correct hash avoids signing complexity. Existing vectors still have conformance value; they simply do not independently prove ES-20 enforcement.

### 2. SHOULD / P2 — large legal integers never receive an independent hash/acceptance oracle

Locations: `internal/verify/hashing.go:16`, `:33`; `internal/verify/verify_test.go:103`; `cli_extremes_test.go:301`, `:331`; fixture 020 line 3; synthetic builder `internal/verify/genesis_ancestry_test.go:135` and `:144`.

Every integer in all 174 records belonging to VALID/PARTIAL vectors fits in uint32 (maximum 1000000); largest legal payload integer anywhere in the fixture corpus is 120000. Both golden preimages contain small integers. Python independently confirmed that replacing each integer's eight-byte encoding with eight bytes containing only its low 32 bits changes **none of those 174 preimages**. All large synthetic chains also use small encoded integer values; the large absolute timestamp is encoded as a string.

The explicit 2^53-1 / 2^53 and int64 cases assert process survival and verdict-format/status agreement only, with zero placeholder hashes. They establish neither correct rejection of oversized integers nor acceptance/hashing of a legal large one. Fixture 020 changes `choice_count` to 2^53 but keeps the old hash; bypassing ES-5 still rejects via HA-14 (and potentially ET-14a). A plausible U64 truncation to uint32, or a parser cap lowered to uint32, therefore has no discriminating legal-input expectation in the suite. The production-backed seal/sign helpers would also compensate for an encoding error if a new synthetic large case used only those helpers.

Add independently expected U64/preimage bytes at 2^32-1, 2^32, 2^53-1 and a correctly hashed opaque payload/version at the legal maximum. Pair with isolated rejection at 2^53 and noncanonical signed/exponent/leading-zero forms. This guards HA-1/HA-4 and ES-5/ES-12/ES-19 separately. Executed evidence: changing `un := uint64(n)` to `un := uint64(uint32(n))` passed the full existing suite. An independently hashed legal opaque payload `n=4294967296` is PARTIAL at 2 on original code but INVALID at 2 under this mutant.

### 3. SHOULD / P2 — malformed type-name checking has no discriminating non-genesis test

Locations: `internal/verify/event.go:51`, `:85`; `internal/verify/verify.go:187` (first-event genesis gate); fixture 021 line 1; `internal/verify/verify_test.go:57`.

The sole malformed-type fixture is capitalized `Genesis` at line 1, with a stale hash. Even replacing `validType` with unconditional true still rejects that line because the first event must be exactly `genesis`, before hashing. The other hand-built input families use legal names. Thus ES-10's charset can disappear without this fixture detecting it.

Add a sealed event after valid genesis with malformed unknown names (uppercase, leading digit/underscore, hyphen, empty, non-ASCII), plus legal single-letter and digit/underscore continuations. Assert INVALID at line 2 for malformed names and PARTIAL at 2 for legal unknown names. This isolates the syntax gate from registry and genesis checks. Executed evidence: the full suite passed after replacing the entire `validType` body with `return true`; an independently sealed malformed-type probe then returned PARTIAL instead of INVALID at 2 under that mutant.

### 4. SHOULD / P3 — CLI bad-usage coverage is narrower than the documented interface

Locations: `chain_report_test.go:190`; `main.go:50`, `:65`, `:77`, `:80`, `:84`, `:93`; API invocation/exit-code sections.

Malformed `--chain` gets a good six-case tool-error table, but there is no corresponding malformed `--head` table, successful `--head=<hash>` case, missing-input case, extra-input case, unknown-flag case, or help case. In particular the separate `--head=` branch could be removed without the existing CLI flag assertions noticing; fixture head options exercise the Go API, not argument parsing. Current source behavior appears correct; this is an actual CLI test gap.

Use a compact table asserting documented status/output/no-report behavior, including both accepted flag forms and flags before/after the path. Do not invent duplicate-flag semantics, since the API does not specify them.

### 5. SHOULD / P3 — the extreme line-count suite inaccurately claims a full walk

Locations: `cli_extremes_test.go:452`–`:464`; `:186`; actual full-walk test `internal/verify/limits_test.go:346`.

`well_formed_lines_200k` repeats a seq-1 genesis-shaped record with payload `p:v` and a zero hash. It fails HA-14 at line 1; it cannot walk 200000 lines. Even sealing that identical line would not yield a full walk because line 2 repeats seq 1. The no-final-newline version also fails first at line 1, rather than exercising final-LF detection after a long chain. The comment explicitly says the well-formed case walks every line, which is false. All these cases still exercise whole-file I/O and endpoint scanning; they are not worthless.

Rename/document their actual early-rejection purpose and reduce duplicated giant inputs where the bounded-allocation test already covers the same path. Preserve the separately built 200000-line `TestManyLines`, which really checks every line and exact affected-line count/endpoints. If end-to-end CLI traversal is intended, use a valid linked chain plus a precise final-line expectation. Do not count this extreme table as additional line-count semantics coverage.

## Accuracy, usefulness and excess conclusions

No definite wrong verdict or blamed-line assertion found. Conservative opaque-ballot expectations align with current ET-24b rather than treating opaque payloads as readable. Fixture-only conformance assertions obey EV-17; advisory-reason assertions outside that harness are legitimate reachability checks, but exact prose/within-line order assertions can burden legal refactors. Reason guards are especially useful when tests reseal only the hash and leave a stale signature.

The suite primarily tests verifier behavior, not a third-party framework. Direct parser flags, threshold behavior and old-implementation comparisons are justified regression checks but should not be represented as independent protocol proof. Small local duplicate endpoint cases are reasonable. The clearest excess is repeated very large early-invalid records with inaccurate traversal claims; synthetic custody acceptance and verbose/stale historical comments are lower-value cleanup. Existing tests need targeted independent cases, not a wholesale rewrite or more raw fixture count.
