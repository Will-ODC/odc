# identity — service rules

- Own database, never exposed, physically separate from ledger.
- The linkage map never appears in any API response, log line, or export. No exceptions.
- Registration: `participant_registered` is **self-signed by the registrant** under its own `pubkey` (`event-types.md` ET-10). Identity never holds or signs with a participant's private key. Ordering: the registration is appended to the ledger first; record linkage only on confirmed append; retries safe (a twice-appended registration is a harmless duplicate). Registrations are `participant_registered` v2, whose signature does not cover `seq`, `ts` or `prev_hash`, so the registrant signs before the line is fixed (ADR-0043 decision 2; the contracts change is owed).
- Registrar, admission half only (ADR-0043): identity holds **no** registrar or operator key and never signs a ballot; the signer (planned, `services/signer/`) holds the registrar key. Identity's eligibility and one-ballot-per-human decision is off-log policy, made before admission and final (ET-20, ET-25). It marks the voter pending, pushes an unattributed `(issue_id, choice)` plus a fresh random request id to the signer, records "voted" only on accepted and rolls back on refused. It sends the signer nothing derived from the voter, keeps only "voter V has voted on issue I" (not the choice), and never learns any ballot's batch, line or signature.
- No receipt (ET-21a): never tell a voter, or anyone acting for them, which line or batch is theirs, and never give a third-party-verifiable statement that a ballot was admitted, appended, or what it chose. An unauthenticated "accepted" or "refused" is allowed.
- v1 = keypairs + pseudonyms; blind signatures later behind this same API.
