# identity — service rules

- Own database, never exposed, physically separate from ledger.
- The linkage map never appears in any API response, log line, or export. No exceptions.
- Registration: `participant_registered` is **self-signed by the registrant** under its own `pubkey` (`event-types.md` ET-10). Identity never holds or signs with a participant's private key. Possession is checked off-log (ADR-0043): link a `pubkey` to a person only after a fresh challenge-response signed by that key (`POST /challenge`); refuse a `pubkey` that is already linked. A `pubkey` already registered on the log but not linked is accepted only when identity's own durable record shows an unfinished submission for that same challenge-verified key (recovery after a crash between append and link), and refused otherwise. Ordering: the registration is appended to the ledger first; record linkage only on confirmed append. A retry of identity's own append is harmless (a twice-appended registration is a duplicate, ET-12); a new submission of an already-registered key is refused. Registrations are `participant_registered` v2, whose signature does not cover `seq`, `ts` or `prev_hash`, so the registrant signs before the line is fixed (ADR-0043 decision 2; the contracts change is owed).
- Registrar, admission half only (ADR-0043): identity holds **no** registrar or operator key and never signs a ballot; the signer (planned, `services/signer/`) holds the registrar key. Identity's eligibility and one-ballot-per-human decision is off-log policy, made before admission and final (ET-20, ET-25). It marks the voter pending, pushes an unattributed `(issue_id, choice)` plus a fresh random request id to the signer, records "voted" only on accepted and rolls back on refused. On a timeout or any other indefinite outcome the signer may already hold the entry, so identity never rolls back: the voter stays pending and identity retries with the same request id until it gets a definite answer, then discards the id (the signer answers any id it already holds "accepted" without admitting again, even after the last seal, so a retry never becomes a second ballot; ET-20). After the issue's last seal, and once every push for it has a definite answer, identity calls the signer's "release issue" endpoint (the signer refuses an earlier release) so the signer can delete that issue's request ids. It sends the signer nothing derived from the voter, keeps only "voter V has voted on issue I" (not the choice), and never learns any ballot's batch, line or signature.
- No arrival time anywhere (ADR-0043): never record when an entry was pushed together with its issue or choice — not in request logs, metrics, traces or retained request ids. Identity keeps a request id only while the push is unresolved.
- No receipt (ET-21a): never tell a voter, or anyone acting for them, which line or batch is theirs, and never give a third-party-verifiable statement that a ballot was admitted, appended, or what it chose. An unauthenticated "accepted" or "refused" is allowed.
- v1 = keypairs + pseudonyms; blind signatures later behind this same API.
