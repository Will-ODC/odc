# ledger — service rules

- Event tables are INSERT-only, enforced at the storage layer; hash computed at insert; seq assigned here.
- Verify before append (`evolution.md` EV-26): never append an event unless the export with it appended as the last line verifies `VALID` under a verifier of exactly this ledger's contracts version, with no `--head` or `--chain`. That covers hash, signatures and keys, and the cross-chain rules such as ET-24 and ET-24a. Keeping the verifier's forward state and checking only the new line is allowed if it reaches the same verdict. A chain not already `VALID` takes no further appends. Never append an unregistered `(type, version)`, or a line over the EV-25 cap (65536 bytes, depth 64).
- Validation needs nothing outside this log: every signing key is on the log (`genesis`, or the event's own `pubkey`). But the ledger is **not** self-contained on the write path: it calls the signer's public API (planned, `services/signer/`), and no other service, on the ballot write path (ADR-0043). A ballot's signature covers its final `seq`, `ts` and `prev_hash` (`hashing.md` HA-15), so the signer can sign only once its line is fixed (ET-17, ET-25). Per ADR-0043, "How the append is coordinated": the ledger decides when to seal and calls the signer to **seal** (it gets back the batch id and counts per choice), orders the batch itself (not by arrival), then makes **one sign call** carrying the batch id, the unsigned payloads in its order, the first `seq`, the `ts` and the first `prev_hash`; the signer assigns positions, chains and signs each ballot in order (each hash covers its `sig`, so the ledger cannot pre-chain them) and returns the signed run. The ledger checks each returned payload equals the one it sent at that index, and holds its tail from the sign call until the run is appended. Before the sign call it persists the sign request, exactly that call's inputs, and on recovery from a crash it replays that request before appending anything else, since the signer signs a batch at one position only and losing the request would strand admitted ballots; it verifies every line before appending (EV-26). That lock spans a call to an operator-run service, never a client round trip. Registrations need no coordination: the ledger writes only `participant_registered` v2, whose signature excludes `seq`, `ts` and `prev_hash`, and only once its embedded verifier registers v2 (ADR-0043 decision 2; the contracts change is owed).
- Ballots are appended in BATCHES (ET-23–ET-25, ET-24a): `ts` quantized to the issue's declared `ballot_batch_interval_ms` (floor 60000); every batch but the issue's last holds at least `ballot_batch_min` (floor 3); an issue never returns to a batch instant it has left, even if the clock steps backwards (ET-24a — a breach is permanent in an append-only log). ET-25: admit a ballot to a batch only after it passes every EV-26 check that does not depend on its position, and refuse it otherwise; **seal** a batch before appending any of it, then append it whole (every admitted ballot, none admitted after the seal), as one run, in an order NOT derived from arrival; at most one unsealed batch per issue; sealed batches appended in seal order; an under-size batch may be sealed only as the issue's last, after which every ballot of that issue is refused before identity records the voter or the signer signs anything for it (ADR-0043). None of ET-25 is verifiable from the log — it is this service's obligation and nobody else can catch a breach of it.
- No receipt (ET-21a): never tell a ballot's submitter, or anyone acting for them, which line or batch is theirs (`seq`, `hash`, `prev_hash`, `sig`, batch instant), and never give a third-party-verifiable statement about the ballot (admitted, appended, or its `choice`). An unauthenticated "accepted" or "refused" is allowed; the public read API is not a receipt.
- Duplicate votes are recorded, not rejected — and cannot be de-duplicated on-log: a ballot carries no voter field (ET-21), so there is nothing to group by. One-ballot-per-human is registrar policy, off-log (ET-20).
- Auth: genesis → its own `operator_pk` (ET-8); issue_created → operator key (ET-13); participant_registered → **self-signed under its own `pubkey`** (ET-10, proof of possession — not the identity service's key); vote_cast → **registrar key** (declared in genesis, held by the signer, not identity; ET-17, ADR-0043). NOT a voter signature — ET-22 permanently bars any voter-held key or voter-produced signature in a ballot.
- Genesis MUST declare registrar_pk != operator_pk (ET-9d). That is one string comparison and it is necessary, not sufficient: two distinct keys can still be held by one party and the log cannot tell, so custody (the signer holds the registrar key, never the operator key, and signs deterministically per RFC 8032 from a reproducible build; ET-9a, ADR-0043) is policy this service depends on and cannot check.
- NEVER open services/verifier or tools/verifier-ts source in the same context as this service.
