# ledger — service rules

- Event tables are INSERT-only, enforced at the storage layer; hash computed at insert; seq assigned here.
- Verify before append (`evolution.md` EV-26): never append an event unless the export with it appended as the last line verifies `VALID` under a verifier of exactly this ledger's contracts version, with no `--head` or `--chain`. That covers hash, signatures and keys, and the cross-chain rules such as ET-24 and ET-24a. Keeping the verifier's forward state and checking only the new line is allowed if it reaches the same verdict. A chain not already `VALID` takes no further appends. Never append an unregistered `(type, version)`, or a line over the EV-25 cap (65536 bytes, depth 64).
- Validation needs nothing outside this log: every signing key is on the log (`genesis`, or the event's own `pubkey`). But the ledger is **not** self-contained on the write path. Every signature covers its event's final `seq`, `ts` and `prev_hash` (`hashing.md` HA-15), so the registrar (identity) can sign a ballot only once its line is fixed, which is at append, after the batch is sealed (ET-17, ET-25). A registrant's `participant_registered` signature has the same binding. How ledger and identity coordinate those appends, and how admission (which knows the voter) is kept apart from signing (which knows the line), is an **open design question**: `memory/OPEN-QUESTIONS.md`, "The registrar signs each ballot's final log position" (S-C, with NS-2). Do not build the write path before it is decided.
- Ballots are appended in BATCHES (ET-23–ET-25, ET-24a): `ts` quantized to the issue's declared `ballot_batch_interval_ms` (floor 60000); every batch but the issue's last holds at least `ballot_batch_min` (floor 3); an issue never returns to a batch instant it has left, even if the clock steps backwards (ET-24a — a breach is permanent in an append-only log). ET-25: admit a ballot to a batch only after it passes every EV-26 check that does not depend on its position, and refuse it otherwise; **seal** a batch before appending any of it, then append it whole (every admitted ballot, none admitted after the seal), as one run, in an order NOT derived from arrival; at most one unsealed batch per issue; sealed batches appended in seal order; an under-size batch may be sealed only as the issue's last, after which every ballot of that issue is refused before the registrar records or signs anything for it. None of ET-25 is verifiable from the log — it is this service's obligation and nobody else can catch a breach of it.
- No receipt (ET-21a): never tell a ballot's submitter, or anyone acting for them, which line or batch is theirs (`seq`, `hash`, `prev_hash`, `sig`, batch instant), and never give a third-party-verifiable statement about the ballot (admitted, appended, or its `choice`). An unauthenticated "accepted" or "refused" is allowed; the public read API is not a receipt.
- Duplicate votes are recorded, not rejected — and cannot be de-duplicated on-log: a ballot carries no voter field (ET-21), so there is nothing to group by. One-ballot-per-human is registrar policy, off-log (ET-20).
- Auth: genesis → its own `operator_pk` (ET-8); issue_created → operator key (ET-13); participant_registered → **self-signed under its own `pubkey`** (ET-10, proof of possession — not the identity service's key); vote_cast → **registrar key** (declared in genesis, held by identity; ET-17). NOT a voter signature — ET-22 permanently bars any voter-held key or voter-produced signature in a ballot.
- Genesis MUST declare registrar_pk != operator_pk (ET-9d). That is one string comparison and it is necessary, not sufficient: two distinct keys can still be held by one party and the log cannot tell, so custody (identity holds the registrar key, never the operator key; ET-9a) is policy this service depends on and cannot check.
- NEVER open services/verifier or tools/verifier-ts source in the same context as this service.
